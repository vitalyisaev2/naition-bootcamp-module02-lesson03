# База телефонных контактов организации (учебный проект, модуль 2, урок 3)

Клиент-серверная адресная книга организации на **Go**, движок хранения написан
с нуля. Веб-интерфейс (TypeScript) и программный API (gRPC + OpenAPI/grpc-gateway).
Хранит имена и телефоны, ищет имена по номеру и номера по имени.

## Постоянные вещи проекта

Эти базовые решения и связи — длинновременные и не меняются от задачи к задаче;
частные детали конкретной фичи живут в её спецификации (`spec/…`), решения — со
ссылками в `decisions/ADR.md`.

### Ключевые принятые решения (кратко)
- **Пишем движок с нуля** (ADR-1): готовые СУБД и embedded-движки запрещены,
  разрешена stdlib Go и чистые алгоритмические библиотеки. Всё ниже пишем сами:
  файловый формат, индексы, WAL, транзакции, репликация.
- **Модель данных двухуровневая** (ADR-3): корпоративный каталог + приватные
  внешние книги.
- **Уникальность телефона по области** (ADR-4): глобальная в каталоге; локальная
  внутри каждой приватной книги.
- **Поиск** — регистронезависимый префиксный, без транслита; только по своей книге
  и каталогу (ADR-5).
- **Репликация** — локальный primary + асинхронные удалённые реплики, stale-чтение
  обязательно помечается (ADR-6).
- **CardDAV отложен** (ADR-7); веб-UI — **TypeScript** (ADR-8).
- **Права** (ADR-13): корпоративный каталог ведёт **администратор каталога**,
  персональные внешние контакты ведёт **сам сотрудник**; чужие приватные книги
  не видит никто.
- **Консенсус** (ADR-14): берём Go-библиотеку Raft как «чистый алгоритм», но лог/
  снапшоты консенсуса — на нашем движке, а fencing/перенос лидера/stale пишем сами.

### Базовые пользовательские пути
Сводно — в `spec/01-user-paths.md` (ПУ-1…ПУ-8). Критичные:
- найти сотрудника по имени / по номеру (каталог);
- добавить и найти приватный контакт (своя книга);
- читать с отставшей реплики — существует обязательный баннер устарелости;
- удалить/изменить запись (tombstone).

### Неочевидные связи (запомнить!)
- **«Один номер под разными именами» исключает дедупликацию.** Пересечение внешних
  контактов ~25% не означает объединение записей — у каждой книги своё имя (I4,
  spec/02). Верхняя оценка ~20 млн записей честна (ADR-2).
- **Уникальность телефона и репликация связаны.** Глобальный инвариант «телефон
  уникален в каталоге» (I2) выполняется, потому что записи идут только на primary в
  одной области; асинхронные реплики просто повторяют лог (spec/03/04).
- **Стале-пометка — это НФ-инвариант.** Чтение с отставшей реплики запрещено
  показывать как «свежее»: либо пометки, либо ничего (spec/04/08). Отсюда поле
  отсталости в API (spec/05) и обязательный баннер в UI (spec/07).

## Структура репозитория
```
README.md                постоянные вещи (здесь)
concepts_brief.md        итог мозгового штурма

spec/
  00-overview.md         цель, глоссарий, источники
  01-user-paths.md       критические пользовательские пути
  02-data-model.md       модель данных и инварианты
  03-storage-engine.md   движок с нуля
  04-replication.md      3 ДЦ, stale-чтение
  05-api.md              gRPC + OpenAPI контракты
  06-search.md           префиксный поиск
  07-ui.md               TypeScript веб-интерфейс
  08-nfr.md              нефункциональные требования
reviews/                 отчёты «золотых рыбок»
```
Рекомендуемый порядок чтения: README → `spec/00` → `spec/01` → `spec/02…08` →
`decisions/ADR.md`.

## Статус
Спецификация в **v0.2**. Ревью «золотых рыбок» (лишнее / недостающее / спорное /
производительность) по паттерну «слон и золотая рыбка» выполнено с теоретическими
и практическими доказательствами; отчёт — `reviews/goldfish_review_report.md`.
Критические находки ревью устранены в спецификации (failover/fencing — spec/04,
стале-пометка — spec/04+ADR-12, поиск по номеру — spec/02/05, НФ-метрики — spec/08,
контракт уникальности — spec/03, версии — spec/02/05, роли каталога — spec/05/07/
01+ADR-13). Код по заданию не пишется (собирается только спецификация).
