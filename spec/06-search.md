# Спецификация — 06. Поиск

> Заземление: ADR-5 (префикс, регистронезависимо, без транслита, область),
> З1 (искать имена по номеру и наоборот), З2.

## Грамматика поиска
- **Префиксный** (совпадение с начала строки) — «Ив» находит «Иван», «Игорь», но не
  «Али**ев**». Промежуточных «серединных» совпадений нет.
- **Регистронезависимый**: индексы и запросы нормализуются (нижний регистр,
  каноническая форма строки) до сравнения; кириллица и латиница сравниваются как
  есть (друг в друга не транслитерируются — нет транслита, ADR-5).
- По **имени** и по **номеру** равноправно: «имя → телефоны» и «номер → имена»
  (З1).
- Точность поиска: целые строки и префиксы; подстроки в середине не ищутся.
- Поиск по номеру использует **две индексированные формы** (canon + stripped) и
  правило частичного ввода из spec/02 «Нормализация» (п. 6), чтобы `+7912…`,
  `912…` и `7912…` покрывались одной из форм.

## Область поиска (прав/приватность)
- **Каталог:** по всем сотрудникам (для любого авторизованного сотрудника).
- **Приватная книга:** только по контактам текущего пользователя (owner_id = я,
  spec/02 I5). По чужим книгам — не ищем (ADR-5).
- Один запрос может комбинировать каталог + свою книгу (например, ПУ-2/ПУ-5) —
  клиент управляет, ответ разделён по источникам (spec/05).

## Реализация поверх движка
- Поиск использует **вторичные индексы** из spec/03: сортированные по
  нормализованному ключу ключи позволяют вести префиксный перекрывающий диапазон
  (range-scan от префикса до конца диапазона) по имени или по номеру в нужной
  области (каталог или книга).
- Результаты дедуплицированы по идентификатору записи.
- **ResolvePhone (сквозной курсор, impl-23):** в режиме `Prefix` два списка
  (catalog + mine) пагинируются **сквозным единым курсором** по объединённому
  байтовому ключу нормализованной формы (единый `PageResult` в proto). Курсор —
  **составной маркер** (позиция catalog-скана + позиция mine-скана + версия записи),
  т.к. catalog и mine физически в разных диапазонах (two LSM), и один токен должен
  восстанавливать позицию в **обоих** потоках, чтобы не было пропусков/дублей на
  стыке источников (design-20). Сортировка — стабильная по объединённому ключу;
  `has_more` относится к объединённому набору. (Одна страница смешивает catalog и
  mine в порядке ключа; различение по типу записи.)

## Сортировка и пагинация (rev v0.2, 🟡 M6/extra resolved)
- Результаты упорядочены **стабильно**: по байтовому порядку нормализованной формы
  (имени/номера) — Unicode-NFC, нижний регистр (для имён); порядок одинаков на
  primary и репликах (согласован). Правило колляции зафиксировано здесь, а не
  «детально реализации».
- **Пагинация по курсору** (не по offset): ответ возвращает **непрозрачный** токен
  следующей страницы; `limit` по умолчанию **50** (настраивается 20–200). Курсор
  кодирует позицию в диапазоне LSM-скана (последний ключ страницы + версия), живёт
  ограниченно (TTL, например 5 минут), не гарантирует стабильность против
  параллельных записей на страницу-назад (базовый порядок может сдвинуться, но без
  искажения и без skip-записей при движении вперёд).
- **Истёкший/невалидный `page_token` (R5-M9):** предъявленный, но протухший или
  malformed курсор → **`VALIDATION_ERROR`** (клиент сбрасывает пагинацию и
  начинает заново с первой страницы); это не молчаливый сброс на страницу 1 и не
  успех. Иначе поведение неуправляемо для UI.
- Для точных значений (полный номер) возвращаются все уникальные совпадения в
  области (в каталоге обычно 1 по I2). Произвольный дамп всей области без
  пагинации не предусмотрен.
