# Спецификация — 01. Критические пользовательские пути

> Путь — текстовое описание от намерения пользователя до результата, а не
> тест-кейс. Здесь — самые частые сценарии; они же служат «скелетом» для
> контрактов (`spec/05`) и тестов при реализации.

## Общий контекст

**Кто пользователь:** сотрудник организации, вошедший в систему под своей
учёткой. Он видит корпоративный каталог (всех) и свою приватную книгу; чужие
приватные книги ему недоступны (ADR-5). Обслуживание каталога ведёт роль
«администратор каталога» (ADR-13); остальные только читают каталог и ведут
свою книгу.

Сводные правила: запись всегда видна владельцу; «поиск» в каталоге — по всем
сотрудникам; «поиск» в приватной книге — только по своим контактам.

## ПУ-1. Найти рабочего сотрудника по имени
1. Пользователь открывает веб-приложение и вводит начало имени («Ив»).
2. Система выполняет префиксный регистронезависимый поиск по корпоративному
   каталогу.
3. Пользователь видит список кандидатов с рабочими телефонами; открывает карточку.
4. **Результат:** имя, должность/отдел, рабочий телефон.

## ПУ-2. Определить владельца номера (искать имя по телефону)
1. Пользователь видит незнакомый номер (с визитки/звонка) и вводит его в поиск.
2. Система ищет по корпоративному каталогу и по приватной книге пользователя
   (номер→имена) — метод `ResolvePhone`, в рамках доступных данных (ADR-5, spec/05).
3. Пользователь видит, кому номер принадлежит в каталоге и/или как он называется
   у него в книге.
4. **Match-режим** (spec/05): полный номер → точное совпадение (Exact); частичный
   ввод → префиксные совпадения (Prefix). **Обязанность задания режима лежит на
   клиенте (struct-5):** клиент для частичного ввода обязан явно передать
   `match_mode=Prefix` (при дефолте `Exact` молчаливый ответ был бы пуст). Частичных
   «серединных» совпадений нет. Если нужен гарантированно-актуальный ответ
   («свободен ли номер») — клиент запрашивает `read_consistency=strong` (spec/05).

## ПУ-3. Добавить приватный контакт
1. Пользователь выбирает «Добавить контакт», вводит имя и телефон.
2. Система проверяет локальную уникальность телефона в книге пользователя; при
   дубликате — отклоняет с понятной ошибкой (ADR-4).
3. Либо добавляет контакт в приватную книгу и подтверждает сохранение.
4. **Результат:** контакт в списке, доступен для поиска по имени и по номеру.

## ПУ-4. Найти контакт в своей книге по имени
1. Пользователь открывает свою книгу и вводит начало имени.
2. Система выполняет префиксный регистронезависимый поиск по приватным контактам
   владельца.
3. Пользователь видит совпадения с телефонами.
4. **Результат:** список контактов с номерами.

## ПУ-5. Найти имя по номеру в своей книге
1. Пользователь вводит чей-то номер и просит найти, как он записан у него.
2. Система ищет номер→имя по приватной книге владельца.
3. **Результат:** имя, под которым номер сохранён у пользователя (если сохранён).

## ПУ-6. Чтение с отставшей реплики (stale-чтение) *(annex: только распределённый профиль)*
1. Пользователь находится на реплике ДЦ, которая обновилась не полностью.
2. Система определяет отсталость и **обязана показать пользователю явное
   уведомление** («данные могут быть устаревшими; ожидается синхронизация, отставание
   N с») — для чтения с отставшей реплики (ADR-6).
3. Пользователь понимает, что может видеть не всё свежее.
4. **Результат:** данные показаны + уведомление о возможной устарелости.

## ПУ-7. Удалить контакт из книги
1. Пользователь удаляет контакт.
2. Система помечает запись tombstone; удаление реплицируется и не «воскрешается»
   (ADR-9).
3. Контакт исчезает из поиска и списков по всем ДЦ после синхронизации.
4. **Результат:** запись больше не находится.

## ПУ-8. Изменить запись (контакт — сотрудник; сотрудника — админ) (rev v0.2, M1)
1. Пользователь меняет запись. Область и право зависят от роли:
   - **ПУ-8a (администратор каталога)** — изменяет запись сотрудника (имя/рабочий
     телефон) в корпоративном каталоге; обычный сотрудник этого делать не может
     (`FORBIDDEN`).
   - **ПУ-8b (любой сотрудник)** — изменяет *свою* приватную запись контакта.
2. Система проверяет уникальность телефона в нужной области (ADR-4), применяет
   изменение атомарно (ADR-9); при заданной ожидаемой версии — `VERSION_CONFLICT`,
   если запись изменилась (spec/02/05).
3. **Результат:** обновлённое значение видно в поиске (после синхронизации — на
   всех ДЦ).

## Карта связей
- ПУ-1, ПУ-2 → поиск по каталогу (`spec/06`, `spec/05`).
- ПУ-3, ПУ-4, ПУ-5, ПУ-7, ПУ-8 → приватная книга (`spec/02`, `spec/05`).
- ПУ-6 → репликация и stale-индикация (`spec/04`, `spec/07`).
- Все пути → атомарность и транзакции (`spec/03`).
