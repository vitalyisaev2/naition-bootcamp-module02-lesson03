# Спецификация — 02. Модель данных

> Заземление: ADR-3 (два пространства), ADR-4 (уникальность по области),
> ADR-9 (удаление/tombstones), З2, З1.

## Две сущности

### Корпоративный каталог — запись сотрудника
| Поле | Тип | Инвариант |
| --- | --- | --- |
| employee_id | ключ, immutable | уникальный глобально |
| full_name | строка | непустая; поиск по префиксу (специально нормализуется, см. spec/06) |
| work_phone | строка (нормализованный номер) | **глобально уникальный** в каталоге (ADR-4); задаёт «один телефон — один сотрудник» |
| external_subject | строка, опционально | постоянный subject-клейм токена сотрудника; путь `principal→employee_id` (ADR-3/5, spec/05 реализация) |
| is_admin | bool, опционально | роль администратора каталога (spec/05 роли) |
| department, title | строка | опционально (справочно) |
| version | монотонно растущий | для атомарных обновлений и репликации |
| deleted | bool (tombstone) | при удалении — data kept, tombstone (ADR-9) |

### Приватная внешняя книга — запись контакта
| Поле | Тип | Инвариант |
| --- | --- | --- |
| contact_id | ключ, immutable | уникальный глобально |
| owner_id | ссылка на employee | владелец книги; определяет область видимости (ADR-5) |
| name | строка | непустая; префиксный поиск |
| phone | строка (нормализованный номер) | **локально уникальный в книге владельца** (ADR-4); **не** уникален глобально — один номер у разных сотрудников зовётся по-разному (З2) |
| version | монотонно растущий | атомарность/репликация |
| deleted | bool (tombstone) | удаление (ADR-9) |

## Нормализация телефонного номера (контракт; ядро = один регион +7)

> Этот раздел — источник истины для правил, на которые ссылаются модель выше и
> spec/08. Реализация обязана ему следовать (инварианты уникальности I2/I3 и
> поиск по номеру зависят от этого контракта). Согласовано со scope-ядром (З1):
> организация среднего бизнеса (ADR-2) обслуживает **единый регион по умолчанию
> `+7`**; многокодовая таблица стран (Беларусь/Украина/Германия/US) **не входит** в
> ядро — вынесена как «если понадобится» в ADR (zoom-2: без спекулятивной
> генерализации). Контракт поэтому прост и детерминирован.

### 1. Обозначения
- **Каноническая форма (canon)** — единственно допустимый вид *хранения* номера:
  символ `+`, затем цифры кода страны и национального номера, без разделителей,
  пробелов, скобок и лидирующих нулей национальной части. Пример: `+79123456789`.
- **Снятая форма (stripped)** — подстрока канонического после кода страны, без `+`.
  Для `+79123456789` → `9123456789`. Индексируется для префиксного поиска по
  локальным (без кода страны) вводам.
- **Вход пользователя (input)** — как ввёл пользователь: цифры и/или `+`, любые
  разделители игнорируются.

### 2. Правило разбора (детерминированное, один регион)
Система поддерживает **один регион по умолчанию: код страны `7`** (Россия; код `7`
также используется Казахстаном, безопасно коллапсирует в тот же canon `+7…`).
Других кодов стран ядро не распознаёт.

Для входного номера:
- **С `+`:** если начинается с `+7` — код извлечён, остальное национальная часть.
  Иные `+`-коды (например `+375…`, `+49…`) — `VALIDATION_ERROR` (ядро их не
  поддерживает; см. «Как расширить на другие страны»).
- **Без `+`:** если начинается с `8` или `7` — национальный код, канонизируется в
  `+7` + (вход без ведущего `8`/`7`, лидирующие нули национальной части срезаются).
  Иначе (вход начинается с любой другой цифры) — трактуется как **национальный
  номер без кода страны** и хранится в снятой форме с кодом по умолчанию `+7`.
- **Тихий ложный canon не строится** (design-1): ввод, не подходящий ни под один
  из разобранных случаев и короче заданной минимальной длины (см. 4), отклоняется
  `VALIDATION_ERROR`, а не подмешивается к `+7` с неправильным результатом.

**Явное правило не-`+` для других кодов:** запись вроде `37529123456` (белорусский
номер без `+`) в ядре **не распознаётся как `+375`** — без `+` она трактуется как
национальная (`+7` + `37529123456`), что некорректно для реального международного
номера. Поэтому **международные номера других стран обязаны вводиться в форме
`+<код>…`**, иначе отклоняются (VALIDATION_ERROR при несовпадении длины/правила).
Это устраняет неоднозначность кодов `8`/`0` (design-4): в ядре только один
лидирующий национальный код `8`/`7` → `+7`.

### 3. Грамматика нормализации (вход → canon + stripped)
1. **Очистка:** убрать все нецифровые символы, кроме ведущего `+`, из `input`.
2. **Разбор кода:**
   - `+`-раскрытие: `+7…` → код `7`; иной `+`-код → `VALIDATION_ERROR`.
   - без `+`: `8…` или `7…` → код по умолчанию `+7`, национальная часть = вход без
     лидирующего `8/7`; иная первая цифра → национальная часть = весь вход, код `+7`.
3. **Каноническая форма** = `+7` + национальная часть (лидирующие нули
   национальной части срезаются). Пустая национальная часть или длина ниже
   минимума → `VALIDATION_ERROR` (п. 4).
4. **Снятая форма** = национальная часть без `+` и кода.

### 4. Минимальная длина (impl-21)
Национальная часть (после кода/лидирующего разбора) должна быть **≥ 7 цифр**
(типичная длина нумерации РФ/КЗ). Иначе — `VALIDATION_ERROR`. Это единственная
числовая граница допустимости в ядре. **Уточнение (design-21):** `≥7` — это
граница **принятия ввода в систему**, а не признак «полного валидного номера»
(фактическая нумерация РФ/КЗ — 10 цифр после `+7`). Exact-поиск по короткому
принятому вводу просто вернёт пустой результат; это молчаливое поведение
фиксируется как ожидаемое, ошибкой не является.

### 5. Формат хранения и префиксный поиск
- В записи (`work_phone`/`phone`) хранится **canon**.
- Во вторичном индексе по номеру хранятся **обе формы** (canon и stripped), чтобы
  префиксный поиск покрывал `+7912…`, `912…` и `7912…` (см. spec/06).

### 6. Поведение неполного/частичного ввода (impl-18)
- Частичный ввод (короче полного) **не нормализуется кодом страны**, а матчится
  как **префикс** по индексированным формам:
  - ввод с `+`, начинающийся с `+7`, матчит префикс canon (напр. `+7912` → `+7912…`);
  - ввод без `+`, начинающийся с `7`, матчит префикс canon (`7912` → `+7912…`) и
    префикс stripped (`912…`); результаты объединяются и дедуплицируются (spec/06);
  - **ввод без `+`, начинающийся с `8` (impl-32):** трактуется как локальный
    лидирующий код (как при полном разборе, п. 2) — `8912…` матчит префикс canon
    `+7912…` и префикс stripped `912…`; иначе префикс `8…` дал бы ложнопустой
    результат вопреки правилу «нет ложнопустого»;
  - ввод без `+`, начинающийся с `9` (не-код), матчит префикс stripped.
- **Нет ложнопустого результата** там, где номер существует: для любой формы
  частичного ввода один из индексированных префиксов покрывается.

### 7. Примеры
| Вход | Canon | Stripped | Статус |
| --- | --- | --- | --- |
| `+7 912 345-67-89` | `+79123456789` | `9123456789` | ok |
| `8 912 3456789` | `+79123456789` | `9123456789` | ok |
| `79123456789` | `+79123456789` | `9123456789` | ok |
| `912345678` | `+7912345678` | `912345678` | ok (без `+`, начинается с `9`) |
| `8912345678` | `+7912345678` | `912345678` | ok (лидирующий `8` → `+7`, impl-32) |
| `+37529123456` | — | — | `VALIDATION_ERROR` (код не `+7`) |
| `123` | — | — | `VALIDATION_ERROR` (нац. < 7) |

### 8. Как расширить на другие страны (вне ядра, ADR)
Многокодовая поддержка (Беларусь `375`, Украина `380`, Германия `49`, US `1`, и
т.п.) — отдельное расширение (новый ADR, не рантайм-конфиг). При вводе следует
добавить longest-prefix-разбор кода, детерминированные tie-break по лидирующим
кодам и национальные лидирующие `0`/`8` с приоритетом. В ядре это намеренно
исключено (ADR-2, zoom-2).

## Семантика version (rev v0.2, 🟡 M5 resolved)
- `version` — **счётчик записи**, монотонно растущий, увеличивается на каждое
  изменение. Не является глобальной последовательностью; для репликации применяется
  порядок лога (LSN), а version — для идемпотентности и разрешения
  обновлений/удалений.
- **Продолжение версионной линии при переиспользовании ключа (R5-B5):** кода
  «номер/`external_subject`» после tombstone вставляется как новая живая запись,
  новая запись получает **`version = удалённая.version + 1`** (см. spec/03
  «Переиспользование»). Это необходимо, чтобы версия всегда монотонно превышала
  удалённую инкарнацию и реплика не «воскрешала» её при применении в LSN-порядке.
- Модель конкурентных обновлений: **optimistic concurrency**. API может принимать
  ожидаемый `version` (клиент указывает версию, которую он видел); при
  расхождении — `VERSION_CONFLICT`. Если версия не указана — применяется
  последняя запись (semantics: server-trivial). Точные правила — в spec/05.

## Инварианты (проверяемые)
- **I1.** employee_id и contact_id глобально уникальны.
- **I2.** В корпоративном каталоге work_phone глобально уникален (ADR-4).
- **I3.** В каждой приватной книге phone уникален «внутри книги»; дубль в одной
  книге отклоняется (ADR-4).
- **I4.** Один и тот же телефон в разных приватных книгах может иметь разные имена.
- **I5.** Чужая приватная книга невидима для поиска (ADR-5): поиск отфильтровывает
  записи по owner_id = текущий пользователь; каталог виден всем.
- **I6.** Удаление — tombstone; после репликации удалённая запись не находится
  в поиске (ADR-9).
- **I7.** Распоряжение после удаления сотрудника (R5-M3): tombstone освобождает
  его `work_phone` и `external_subject` для новой записи (переиспользование, spec/03);
  принадлежащие удалённому `owner_id` private-строки **не переназначаются** новому
  владельцу и сохраняются (retention/GC — вне ядра, политика). Осиротевшие строки
  остаются scoped по старому `owner_id` и недоступны после потери привязки.

## Репликация модели
- Каталог и приватные книги — единый поток записей в движке (spec/03);
  принадлежность к каталогу/книге задаётся типом записи и owner_id (для приватных).
- Такая запись реплицируется целиком (спец. spec/04).

## Примечание о «пересечении 25%»
- Требование «у двух случайных сотрудников внешние контакты пересекаются на 25%»
  (З2) означает, что **один и тот же номер физически встречается в разных книгах**,
  но объединять записи нельзя — у каждого книга хранит своё имя (I4). Поэтому
  дедупликация не даёт экономии, а верхняя оценка объёма — честные
  100 тыс. × 200 ≈ 20 млн записей (ADR-2, spec/08).
