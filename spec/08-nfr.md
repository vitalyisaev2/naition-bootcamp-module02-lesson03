# Спецификация — 08. Нефункциональные требования

> Заземление: З1 (пример «отвечает менее чем за 20 мс в 99% случаев», «реально
> много записей», «надёжно»), З2 (масштаб, 3 ДЦ, атомарность), ADR-2/6/9, spec/03/04.

## Масштаб (ADR-2)
- До **100 тыс. сотрудников** (записи корпоративного каталога).
- До **200 внешних контактов** на сотрудника → до **20 млн записей** приватных книг.
- Каталог + приватные книги: единый поток записей в движке (spec/03); верхняя
  оценка диска и индексов — из этого объёма.

## Производительность
| Метрика | Целевое значение |
| --- | --- |
| Задержка точечного чтения (get по ключу) | p99 < 10 мс (primary) |
| Задержка префиксного поиска 1-й страницы | p99 < 20 мс (primary); на отставшей реплике — см. stale-пометку, задержка аналогичная |
| Задержка записи (commit) | p99 < 20 мс на primary (локальный кворум, ADR-6) |
| Пропускная способность записи | поддерживать групповой commit (spec/03) без потери атомарности |
| Параллельность | множество читателей и писателей; MVCC-снапшоты не блокируются длинными записями (spec/03) |

> Базальные значения задаём как НФ-таргеты на этом этапе; точные цифры уточняются
> бенчмаркингом реализации (пункт про производительность — зона «золотой рыбки»).

### Бюджеты и недостающие НФ-метрики (rev v0.2, блокер B4 resolved)
- **Область действия p99 (критично, блокер B4):** заявленные задержки
  (`<10 мс` чтение, `<20 мс` поиск/запись) валидны для клиента, **физически
  близкого к обслуживающему ДЦ (внутри его региона/луна)**. Для клиента, чей
  cross-region RTT к primary > 20 мс действуют отдельные таргеты (см. geo-affinity
  ниже); иначе таргет недостижим по построению.
- **Пиковая нагрузка (RPS):** требуется задать до бенчмаркинга, напр.
  `write-RPS ≥ 200`, `read-RPS ≥ 5000` на каталог общ. нагрузки; числа калибруются
  по 20 млн записей и P99-таргетам. (Открытый числовой пункт для бенчмарк-фазы.)
- **Бюджет памяти:** memtable + Bloom-фильтры + block cache подлежат бюджету;
  целевой FPR Bloom ≤ 1% (напр. 10 бит/ключ), поддержание числа ран и размера
  memtable как параметры конфигурации (см. spec/03).
- **Бюджет компакции:** задать write-amplification ceiling и допустимое время
  write-stall на major compaction (иначе p99 деградирует непредсказуемо). Цифры —
  бенчмарк-фаза.
- **Class хранилища/fsync:** предполагается локальный NVMe/SATA SSD с известным
  бюджетом fsync; без этого p99 записи (fsync-путь) не гарантируется.
- **Проверка уникальности (M3):** стоимость unique-check (CAS lookup телефона)
  входит в бюджет задержки записи (spec/03).

## Отказоустойчивость и репликация (spec/04)
- Топология: **3 геораспределённых ДЦ** (З2).
- Потеря **одного** удалённого ДЦ не останавливает чтения и записи.
- **RPO:** ненулевой (асинхронные удалённые реплики, ADR-6); допустимое отставание
  реплики — **порог `T_stale`**, числовой по умолчанию **≤ 5 с** (настраивается).
  RPO = накопленное отставание на момент сбоя primary (spec/04); если требуется
  строже — глобальный кворум (ADR-6).
- **RTO потеря primary:** запись переживает **промоушен read-реплики** (spec/04,
  failover); таргет RTO по умолчанию **≤ 5 минут** (auto или ручной промоушен —
  режим настраивается). Обеспечивается fence/epoch (блокер B2).
- **Geo-affinity (блокер B4):** клиент обслуживается **ближайшим ДЦ** (чтение);
  запись идёт в primary (роутинг через discovery, spec/04). Таргеты p99 валидны для
  клиента у своего ДЦ; для кросс-регион клиента применимы отдельные (увеличенные)
  таргеты.
- **Stale-чтение:** допустимо **только с пометкой** пользователю (ADR-6, spec/04/07).
  Правило безопасности пометки: никогда не сообщать «свежие» при возможной
  устарелости; `current` = отставание < `T_stale`, иначе `stale` (spec/04).

## Durability (spec/03)
- Политика fsync: (а) per-commit для каталога и ценных записей — **0 потерянных
  закоммиченных записей при аварийной остановке одиночного узла** (fsync-per-commit,
  локальный кворум; для каталога групповой commit не применяется — см. M7);
  (б) батч-режим для высоконагруженных приватных книг — ограниченное окно потерь
  при сбое до fsync (окно по умолчанию ≤ 1 с, настраивается).
- **Разграничение потери (M8/disputable G):** «0 потерь» распространяется только на
  падение одиночного узла (fsync-per-commit). При потере **всего первичного региона**
  записи, принятые локальным кворумом, но не доставленные на промоут-ДЦ, теряются
  (объём ≤ отставания = RPO). Это явно отличать от «0 потерь» локального случая.
- Восстановление после аварийной остановки — без рассинхронизации индексов (spec/03).

## Атомарность и конкурентность (ADR-9)
- Множественные параллельные читатели и писатели (З1).
- Каждая изменяющая операция — атомарная транзакция; snapshot (MVCC) изоляция
  чтений (spec/03).
- Инварианты уникальности телефона (I2/I3) соблюдаются при конкурентных вставках
  в пределах области (ADR-4).

## Безопасность
- Аутентификация вызывающей стороны (сотрудник); доступ только к своим данным
  в приватной книге (ADR-5, spec/02 I5/I6).
- TLS для API (spec/05). Детали identity/policy — в части безопасности, сужается
  при реализации (см. «границы, требующие уточнения»).

## Наблюдаемость
- Трассируемость RPC (correlation/trace id) для поиска инцидентов (spec/05).
- Метрики отсталости реплик (для пометки stale, spec/04) и метрики движка
  (размер ран, компакция, WAL-позиция) — для эксплуатации.

## Границы, требующие уточнения при реализации
- Модель прав/ролей (кто правит каталог) — см. spec/05, вопрос открыт для согласования
  (M1); конкретные параметры бенчмаркинга (RPS, бюджет памяти/компакции);
  конкретный каталог кодов стран для нормализации телефона; точные пороги
  компакции. Это открытые пункты, не контракты сами по себе.
