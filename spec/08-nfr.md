# Спецификация — 08. Нефункциональные требования

> **Границы (scope-mark):** распределённые НФ (3 ДЦ, RPO/RTO/T_stale,
> geo-affinity, fencing-доступность) — **вне З1**, добровольное расширение
> (З2/ADR-10, см. spec/00). НФ **ядра** (задержки движка и поиска, масштаб,
> durability, атомарность, безопасность) — обязательные. Для «однодцовой»
> (ядро-only) конфигурации распределённые пункты не применяются как контракты.

> Заземление: З1 (пример «отвечает менее чем за 20 мс в 99% случаев», «реально
> много записей», «надёжно»), З2 (масштаб, 3 ДЦ, атомарность), ADR-2/6/9/10/11/12,
> spec/03/04.

## Масштаб (ADR-2)
- До **100 тыс. сотрудников** (записи корпоративного каталога).
- До **200 внешних контактов** на сотрудника → до **20 млн записей** приватных книг.
- Каталог + приватные книги: единый поток записей в движке (spec/03); верхняя
  оценка диска и индексов — из этого объёма.

## Производительность
| Метрика | Целевое значение |
| --- | --- |
| Задержка точечного чтения (get по ключу) | p99 < 10 мс (primary) |
| Задержка префиксного поиска 1-й страницы | p99 < 20 мс (primary); на отставшей реплике — см. stale-пометку, задержка аналогичная |
| Задержка записи (commit) | p99 < 20 мс на primary (локальный кворум, ADR-6) |
| Пропускная способность записи | поддерживать групповой commit (spec/03) без потери атомарности |
| Параллельность | множество читателей и писателей; MVCC-снапшоты не блокируются длинными записями (spec/03) |

> Базальные значения задаём как НФ-таргеты на этом этапе; точные цифры уточняются
> бенчмаркингом реализации (пункт про производительность — зона «золотой рыбки»).

### Бюджеты и недостающие НФ-метрики (rev v0.2, блокер B4 resolved)
- **Область действия p99 (geography-ограничение):** заявленные задержки
  (`<10 мс` чтение, `<20 мс` поиск/запись) валидны для клиента, **физически
  близкого к обслуживающему ДЦ (внутри его региона/луна)**. Для клиента, чей
  cross-region RTT к primary > 20 мс действуют отдельные таргеты (см. geo-affinity
  ниже); иначе таргет недостижим по построению.
- **Пиковая нагрузка (RPS), закреплены как цели (impl-25):** `write-RPS ≥ 200`,
  `read-RPS ≥ 5000` (суммарно по ядру). Это контрактные первичные таргеты для
  калибровки p99 и компакции; уточняются бенчмарк-фазой, но служат обязательной
  исходной оценкой, а не «напр.».
- **Бюджет памяти (числовой, impl-15):** на узел при 20 млн записей (оценка: ~200 байт/запись × 20 млн ≈ 4 ГБ сырых данных + индексы) — целевой лимит **≤ 8 ГБ/нода** (memtable + Bloom-фильтры + block cache совместно), параметры конфигурируются под этот предел. Целевой FPR Bloom ≤ 1% (напр. 10 бит/ключ).
- **Бюджет поиска (диапазонные сканы, v0.4):** для префиксного range-скана через
  несколько ран учтён бюджет на чтение — p99 1-й страницы < 20 мс (см. таблицу), с
  ограничением числа ран и уровнем компакции; Bloom-фильтры точке не покрывают
  range (см. spec/03 Alternatives).
- **Бюджет компакции:** write-amplification ceiling **≤ 15×** (уровневая компакция,
  типичный диапазон LSM), допустимый **write-stall** (приостановка записи на major
  compaction) — **≤ 5 с единично**, целевой — укладываться в p99 записи (spec/08),
  иначе p99 деградирует непредсказуемо. Цифры валидируются бенчмарк-фазой.
- **Class хранилища/fsync:** предполагается локальный NVMe/SATA SSD с известным
  бюджетом fsync; без этого p99 записи (fsync-путь) не гарантируется.
- **Проверка уникальности (M3):** стоимость unique-check (CAS lookup телефона)
  входит в бюджет задержки записи (spec/03).

## Отказоустойчивость и репликация (spec/04)
- Топология: **3 геораспределённых ДЦ** (З2).
- Потеря **одного** удалённого ДЦ не останавливает чтения и записи.
- **RPO:** ненулевой (асинхронные удалённые реплики, ADR-6); допустимое отставание
  реплики — **порог `T_stale`**, числовой по умолчанию **≤ 5 с** (настраивается).
  RPO = накопленное отставание на момент сбоя primary (spec/04); если требуется
  строже — глобальный кворум (ADR-6). **К составу потерь добавлен окно ack-loss
  (design-18):** записи, принятые/подтверждённые old-primary между потерей связи с
  регулятором и self-fence (≤ 2×`T_lease` ≈ 60 с), при промоушене теряются —
  это дополнительный член потерь сверх репликационного отставания (spec/04
  «Окно ack-loss в RPO»). **Эффективный RPO (R5-M4):** с учётом доминирующего
  ack-члена явная цифра для эксплуатационного бюджета — **`RPO_eff = T_stale +
  2·T_lease ≈ 65 с`** (ack-член ≈ 60 с + отставание ≤ 5 с). Оператор и настройки
  бюджетрируют против `RPO_eff`, а не 5 с (иначе обязательство больше бюджета).
  Эксплуатационная митигация: router по детекту потери
  primary прекращает направлять запись на кандидата фейлоувера (через discovery),
  сужая окно.
- **RTO потеря primary:** запись переживает **промоушен read-реплики** (spec/04,
  failover); таргет RTO по умолчанию **≤ 5 минут** (auto или ручной промоушен —
  режим настраивается). Обеспечивается fence/epoch. **Смета (design-5):**
  RTO = авто-детект потери primary (≤ 60 с) + fencing time (запас 2×`T_lease`,
  ≤ 60 с) + сборка нового кворума/догон хвоста (≤ 60 с) + запас на skew ≤ 5 с —
  сумма укладывается в 5 мин. **Критерий выбора промоут-реплики (design-3):**
  промоутится реплика с наименьшим лагом и лагом ≤ RPO (`T_stale`); иначе промоут
  блокируется/переводится в операторный режим (иначе потеря > RPO).
- **Geo-affinity:** клиент обслуживается **ближайшим ДЦ** (чтение);
  запись идёт в primary (роутинг через discovery, spec/04). Таргеты p99 валидны для
  клиента у своего ДЦ; для кросс-регион клиента применимы отдельные (увеличенные)
  таргеты.
- **Stale-чтение:** допустимо **только с пометкой** пользователю (ADR-6, spec/04/07).
  Правило безопасности пометки: никогда не сообщать «свежие» при возможной
  устарелости; `current` = отставание < `T_stale`, иначе `stale` (spec/04).
- **Каденция опорной точки (heartbeat) для `current` (design-19):** позиция
  primary (по которой реплика оценивает отставание) распространяется heartbeat-ом
  с каденцией **≤ 1–2 с**, т.е. заметно меньше `T_stale` (5 с). Иначе категория
  `current` недоказуема из-за погрешности опорной точки; при нарушении каденции
  реплика обязана ставить `stale` по умолчанию.

## Durability (spec/03)
- Политика fsync: (а) per-commit для каталога и ценных записей — **0 потерянных
  закоммиченных записей при аварийной остановке одиночного узла** (fsync-per-commit,
  локальный кворум; для каталога групповой commit не применяется — см. spec/03
  и ADR-9);
  (б) батч-режим для высоконагруженных приватных книг — ограниченное окно потерь
  при сбое до fsync (окно по умолчанию ≤ 1 с, настраивается).
- **Разграничение потери (ADR-9/spec/03):** «0 потерь» распространяется только на
  падение одиночного узла (fsync-per-commit). При потере **всего первичного региона**
  записи, принятые локальным кворумом, но не доставленные на промоут-ДЦ, теряются
  (объём ≤ отставания = RPO). Это явно отличать от «0 потерь» локального случая.
- Фencing/lease (spec/04): при **недостижимости epoch-регулятора** запись
  приостанавливается (fail-closed), чтения stale. Первичность узла ограничена
  сроком lease `T_lease`=30 с, запас 2×, период продления `T_lease/3`≈10 с.
  **Требование к часам:** серверы синхронизируют время по NTP; max clock-skew
  между узлами и регулятором — **≤ 5 с** (иначе гарантия 2× недоказуема, spec/04).
- Восстановление после аварийной остановки — без рассинхронизации индексов (spec/03).

## Атомарность и конкурентность (ADR-9)
- Множественные параллельные читатели и писатели (З1).
- Каждая изменяющая операция — атомарная транзакция; snapshot (MVCC) изоляция
  чтений (spec/03).
- Инварианты уникальности телефона (I2/I3) соблюдаются при конкурентных вставках
  в пределах области (ADR-4).

## Безопасность
- Аутентификация вызывающей стороны (сотрудник); доступ только к своим данным
  в приватной книге (ADR-5, spec/02 I5/I6).
- TLS для API (spec/05). Детали identity/policy — в части безопасности, сужается
  при реализации (см. «границы, требующие уточнения»).

## Наблюдаемость
- Трассируемость RPC (correlation/trace id) для поиска инцидентов (spec/05).
- Метрики отсталости реплик (для пометки stale, spec/04) и метрики движка
  (размер ран, компакция, WAL-позиция) — для эксплуатации.

## Границы, требующие уточнения при реализации
- Модель прав/ролей — уже задана (ADR-13, spec/05/07); уточняются только детали
  политики токена. Конкретные параметры бенчмаркинга (RPS, точные FPR/Bloom,
  пороги компакции) калибруются по заложенным бюджетам; правила нормализации
  телефона — раздел «Нормализация» в spec/02 (многокодовая таблица стран — вне
  ядра, отдельный ADR, не контракт). Это открытые пункты имплементации, не
  контракты сами по себе.
