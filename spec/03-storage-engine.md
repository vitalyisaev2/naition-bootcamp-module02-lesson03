# Спецификация — 03. Движок хранения (пишется с нуля)

> **Границы (scope-mark):** движок и его требования (spec/03) относятся к **ядру**
> системы, прямо требуемому З1. (Части про реплицируемость WAL/логики подпирают
> распределённый слой spec/04 — он вне З1, добровольное расширение по З2/ADR-10;
> ядро работоспособно и без него.)

> Заземление: ADR-1 (граница «с нуля»), ADR-9 (атомарность/транзакции),
> З2, З3 (LSM-tree: O'Neil et al. 1996; архитектура LevelDB/RocksDB).

## Цель и границы
Самописный слой персистентности на Go (ADR-1): стандартная библиотека Go
разрешена; готовые СУБД и embedded-движки запрещены. Поддерживает записи
модели из `spec/02`, атомарные обновления нескольких индексов, префиксный поиск
(`spec/06`), множественные читатели/писатели.

## Архитектура (LSM-подход)
Выбираем log-structured merge (LSM) — отраслевой стандарт для in-memory-fresh +
накопительных данных (LevelDB, RocksDB); мы реализуем его сами.

### Alternatives Rule: почему LSM, а не B-tree (требование стандарта; обосн. v0.4)
Обязательная оценка альтернативы. Рассмотрена каноническая **B-tree / B⁺-tree**
страница-в-узле структура вместо LSM. Отклонена, но **честно по реальному профилю
нагрузки** (раунд 2 design-16): система **read-тяжёлая** (`read-RPS ≥ 5000` против
`write-RPS ≥ 200`, spec/08), доминирующий запрос — **префиксный range-scan**
(spec/06), запись редкая.
- **Range-сканы по B⁺-tree конкурентны, но дороги на поддержание.** B⁺-tree
  отлично сканирует листья по порядку, однако для **нескольких вторичных индексов**
  (первичный + name + phone в каталоге; owner,name + owner,phone в книге) требует
  согласованного обновления каждого индекса при каждой записи. При редкой записи
  это приемлемо, но даёт **случайные page-записи** во многих B-деревьях одновременно
  и удерживает в памяти структуру индексов целиком.
- **Главный аргумент — управляемое переиспользование номеров (tombstones/версии,
  ADR-9).** B-tree плохо компактит удалённые версии/tombstone и переиспользование
  ключа (I2/I3, удаление номера → вставка того же номера) — требует прямого удаления
  из листа и перебалансировки. LSM выполняет **фоновую компакцию** старых версий и
  tombstone за амортизированную стоимость, не блокируя чтения. Это решающий фактор
  для нашей модели данных.
- **Write-амплификация (признаём, что это не главный довод, но дополняет).**
  LSM агрегирует случайные вставки в последовательные memtable-флаши.
- **Параллельные читатели/писатели + group commit (spec/08).** LSM с MVCC
  снапшотами и group commit даёт предсказуемые батчи записи без page-level
  локировки в стиле B-tree.
- **Затраты LSM (признаны и митигированы честно, v0.4):** (а) для префиксных
  range-сканов через несколько ран слияние на чтении — **Bloom-фильтры НЕ
  помогают диапазонам** (они только на точечный lookup). Поэтому ложное смягчение
  убрано; реальные митигации — **числовой бюджет на поиск в spec/08**, понижение
  числа ран `level`-компакцией и **write-stall-бюджетом ≤ spec/08** (≤ 5 с). (б)
  write-amplification при компакции ограничена budget-ами spec/08. Для 20 млн
  записей и префикс-поиска LSM — лучший баланс с учётом честной оценки затрат.
  Источник: LSM (O'Neil et al., 1996), архитектура LevelDB/RocksDB (З3).
- **Прямое сравнение по преобладающему запросу (range-scan) приведено в spec/08**
  (бюджет поиска), чтобы не оставлять разрыв между выбором и метрикой.

1. **WAL (write-ahead log)** — append-only поток операций на диске, fsync-батчами.
   Отвечает за восстановление после сбоя (durability). Каждая закоммиченная
   транзакция = одна запись WAL.
2. **Memtable** — отсортированная in-memory структура (например, skip list) с
   последними записями. Параллельные читатели видят согласованную версию через
   MVCC-снапшоты.
3. **Immutable-раны (SSTable-подобные)** — замороженные отсортированные файлы на
   диске, получаемые при flush memtable.
4. **Compaction** — фоновая чистилка: склейка ран, выкидывание старых версий и
   tombstone-удаление.
5. **Bloom-фильтры** — на каждую рану, чтобы точечные чтения (по ключу/номеру) не
   сканировали лишние файлы.

### Индексы (для модели spec/02)
- Первичный индекс по ключу (employee_id / contact_id).
- Вторичные индексы для префиксного поиска, ключ — нормализованная строка
  (имени или номера) с порядком сортировки; перекрывают диапазоны-префиксы
  (spec/06):
  - Каталог: `name → employee_ids`, `work_phone → employee_id`.
  - Приватная книга: `(owner_id, name) → contact_ids`, `(owner_id, phone) → contact_id`.
- Индексы обновляются **атомарно вместе с записью** (см. транзакции).

## Транзакции, атомарность, изоляция
- Единица изменения — операция, меняющая запись + все связанные индексы.
- **Commit = одна запись WAL**; применение к memtable/индексам атомарно. При сбое
  WAL повторяет незавершённое так, что все индексы согласованы (нет «полуобновлений»).
- **Изоляция:** snapshot (MVCC) — читатель не видит «наполовину закоммиченную»
  операцию (ADR-9).
- **Group commit** — батчинг fsync нескольких операций для пропускной способности
  (компромисс с задержкой одиночной записи, см. spec/08).
- **Проверки инвариантов** (I2/I3, уникальность телефона) выполняются до commit и
  атомарны: конкурентные вставки не дублируют телефон в рамках области
  уникальности (ADR-4). **Обязательный механизм (блокер M3 revised):** записи в
  одну область уникальности сериализуются на единственном primary (детерминированный
  строгий порядок применения); уникальность проверяется как **compare-and-set по
  ключу телефона** в той области (каталог — глобально; книга — по owner), а **не**
  «прочесть-потом-записать» через MVCC-снапshot (snapshot-чтение не даёт
  сериализации read-then-write). Гарантия обязана держаться даже при конкурентных
  вставках. Стоимость unique-check входит в бюджет задержки записи (spec/08).
- **Тот же CAS-механизм распространяется на `external_subject` (design-17):**
  уникальность привязки principal→employee_id (spec/05) — тоже инвариант записи, а
  не реализационная деталь. Движок обязан сериализовать вставки по **ключу
  `external_subject`** (единичное-соответствие) тем же compare-and-set-механизмом,
  что и телефон, чтобы конкурентные `CreateEmployee` с одинаковым subject не
  создали двух записей (иначе scoping I5 и подмена владельца/привилегии). Дубль
  `external_subject` → `DUPLICATE_SUBJECT`. **Lifecycle (R5-B4):** привязка
  иммутабельна на время жизни живой записи (очистка/смена через API запрещена);
  при tombstone ключ освобождается для новой записи — та же политика, что и для
  номера (переиспользование ниже), с теми же гарантиями против «воскрешения».
- **Переиспользование номера после удаления (ядровой контракт, M4; перенесён из
  spec/04 по zoom-2):** единственный-ключ уникальности действует по **живым**
  записям — tombstone не блокирует вставку того же номера как нового живого.
  Чтобы при репликации/компакции не «воскресить» старый живой дубликат: tombstone
  хранит исходный номер и version и удаляется только компакцией по истечении
  срока. **Начало версии новой записи (R5-B5):** version — счётчик записи,
  стартующий с 1 (spec/02), поэтому «свежая» запись не обязана больше версии
  tombstone навскидку. Для гарантии монотонного роста сверх удалённой инкарнации
  новая живая запись по тому же ключу получает **`version = tombstone.version + 1`**
  (продолжение версионной линии области ключа). Тогда реплика, применявшая delete
  (высокая version) и create (version на 1 больше), применяет в LSN-порядке без
  само-отмены и «воскрешения». Окно между удалением и GC не создаёт в поиске дублей
  одного номера (I6/I2/I3 соблюдаются по живым записям).
- Точные структуры уникальность-индекса (в-памяти set / on-disk hash с достоверением
  при bloom-ложноположительных), политика update в той же WAL-записи — детали
  реализации, но обязанность сериализации и CAS (телефон и subject) — контракт,
  не «на усмотрение».

## Durability
- Политика fsync настраивается: (а) на каждую транзакцию, (б) групповой батч
  (по таймеру/порогу). Уровень (а) даёт строгую durability для ценных записей
  (каталог), (б) — компромисс для высоконагруженных приватных книг. Значения
  параметров — в spec/08.
- Восстановление: при старте WAL проигрывается; memtable пересобирается; незакрытые
  частичные операции откатываются (согласованность индексов).

## Объём и отказоустойчивость (уровень движка)
- Целевой объём ~20 млн записей (ADR-2). Дисковая модель допускает рост за счёт
  компакции и multiple data dirs (детали — spec/08).
- Аварийная остановка (без корректного закрытия) не должна приводить к потере
  закоммиченных данных при политике (а) и к рассинхронизации индексов.

## Открытые для реализации решения (не блокируют спеку)
- Точные структуры (skip list vs. b-tree memtable), размер flush-порога и
  стратегия компакции (level vs. size-based) — на усмотрение реализации при
  соблюдении контрактов выше.
