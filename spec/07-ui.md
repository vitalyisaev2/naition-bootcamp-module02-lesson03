# Спецификация — 07. Веб-интерфейс

> Заземление: З2 (веб-приложение обязательно, современный стек JS/TS),
> ADR-8 (TypeScript), spec/01 (пути), spec/04 (стале-чтение), spec/05/06 (API/поиск).

## Технология
- Веб-приложение в браузере на **TypeScript** (ADR-8); фреймворк (React/Vue/...)
  — осознанно открытый пункт (не влияет на контракты API; фиксируется на этапе
  генерации проекта, impl-17).
- Общается с бэкендом через собственную API, затем публикуемую как
  HTTP/OpenAPI через grpc-gateway (spec/05). Типы для клиента — из proto (spec/05).

## Экраны (соответствуют путям spec/01)
1. **Поиск по каталогу.** Поле ввода → список сотрудников (префикс по имени,
   spec/06), карточка: имя, должность/отдел, рабочий телефон. (ПУ-1)
2. **Поиск по номеру.** Ввод номера → кто в каталоге + как назван у меня в книге. (ПУ-2, ПУ-5; метод `ResolvePhone`, spec/05)
3. **Моя книга.** Список приватных контактов; добавление/изменение/удаление;
   локальный префиксный поиск по имени/номеру. (ПУ-3, ПУ-4, ПУ-7, ПУ-8)
4. **Баннер устарелости *(annex: только распределённый профиль)*.** Если чтение
   пришло с отставшей реплики,
   UI **обязан** показать явное уведомление «данные могут быть устаревшими;
   ожидается синхронизация, отставание N с» (ADR-6, spec/04). Уведомление не
   снимается самопроизвольно, пока значение не `current`. В однодцовой
   (ядро-only) конфигурации, где отставших реплик нет, этот экран не применяется.
5. **Каталог (только для администратора, M1 resolved).** Управление записями
   сотрудников: добавить/изменить/удалить, поиск по каталогу для правки.

## Поведенческие требования UI
- **Пагинация** поисковых результатов (по курсору, spec/06): не выгружать все
  результаты сразу.
- **Обработка ошибок API:** типизированные ошибки (`DUPLICATE_PHONE`,
  `DUPLICATE_SUBJECT`, `NOT_FOUND`, `VERSION_CONFLICT`, `VALIDATION_ERROR`,
  `FORBIDDEN`, `SERVICE_UNAVAILABLE` — канонический список spec/05) отображаются
  понятным текстом
  (например, «Такой номер уже есть в вашей книге» — при добавлении, ПУ-3).
  **Различение по detail (R5-B1):** поскольку `DUPLICATE_PHONE` и `DUPLICATE_SUBJECT`
  мапятся в один gRPC-статус `AlreadyExists`, UI различает сценарии **по
  типизированному detail** (reason = канонический код, spec/05), а не парсингом
  сообщения. Истёкший/невалидный курсор (spec/06) → «повторите запрос заново».
- **Формы валидируют** телефон до отправки (формат), но финальную уникальность
  проверяет сервер (конкурентный случай, ADR-9/I3).
- **Доступ только к своим данным** в «Моей книге»; чужих книг в интерфейсе нет (ADR-5).
- Состояние «пишет на primary» по умолчанию; пометки про реплику появляются при
  чтении с реплики (spec/04).

## Доступность и наблюдаемость
- UI показывает понятные состояния сети/ошибок: офлайн/нет соединения, недоступный
  бэкенд (`SERVICE_UNAVAILABLE`), ретраи транзиентных ошибок; тостовые уведомления
  о сетевом сбое не блокируют интерфейс.
- Трассировка запросов к API (correlation id) — для отладки (НФ, spec/08).

## Права и экраны (rev v0.2, M1 resolved)
- **Обычный сотрудник:** экраны 1–4 (поиск каталога, поиск по номеру, моя книга,
  баннер устарелости); правит только свою книгу; каталог — только для чтения.
- **Администратор каталога:** дополнительно видит **экран «Каталог»** — управление
  записями сотрудников (добавить/изменить/удалить, ведение списка). Чужие приватные
  книги в UI админа отсутствуют (принцип владельца, spec/05).
- Меню/экраны по роли; неавторизованное действие скрывается и защищено на сервере
  (`FORBIDDEN`, spec/05).
