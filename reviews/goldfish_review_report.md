## 🔴 Блокеры

### B1. Failover первичного региона невозможен в заявленной топологии
- **Линзы:** missing, disputable
- **Где:** `spec/04` (топология), `spec/04` (failover)
- **Разрыв:** Raft-кворум описан только «внутри первичного региона» (3+ узлов);
  удалённые ДЦ — «read-реплики» без ролей для записи и без членства в группе.
  Раздел failover требует «Raft-перевыбор на оставшихся узлах», но оставшиеся
  узлы не входят в Raft-группу → перевыбор невозможен, реальной процедуры
  восстановления primary нет (противоречие, подтверждено скрестом инвариантов и
  `grep Raft`).
- **Рекомендация:** определить явную процедуру промоушена read-реплики до нового
  primary с осознанной потерей «хвоста» unreplicиврованного WAL (ограниченного
  отставанием = RPO) и с fencing/epoch; либо включить удалённые ДЦ в консенсус
  (глобальный кворум — тогда пересмотреть ADR-6 и p99); либо явно зафиксировать
  «ручной промоушен с перерывом записи».

### B2. Риск «split-brain» для глобальной уникальности телефона (I2)
- **Линзы:** disputable
- **Где:** `spec/02` (I2), `spec/04` (failover), README
- **Разрыв:** уникальность держится на «записи идут только на primary». При
  перегородке/задержке (не гибели) старого primary и промоушене реплики по
  таймауту два «каталога» одновременно принимают вставки → I2 нарушается
  неотменимо. Fencing/lease/epoch не введены.
- **Рекомендация:** ввести epoch/lease и правило «промоушен возможен только после
  конца эпохи старого primary»; требование зафиксировать в NFR.

### B3. Stale-пометка неразрешима в чистом async: «current» невычислим
- **Линзы:** disputable, missing, performance
- **Где:** `spec/04` (stale-чтение), `spec/05`, `spec/08`
- **Разрыв:** async-реплика не знает актуальный LSN primary без синхронного запроса.
  Либо каждый read делает sync-round-trip (теряем асинхронность), либо «current»
  недоказуем → по безопасному правилу «никогда не свежее» пришлось бы помечать всё.
  Дилемма не разрешена.
- **Рекомендация:** определить отсталость по порогу лага относительно
  last-known-положения primary (heartbeat/координация лога), а не по точной
  свежести; `current` = лаг ниже порога; окно недостоверности всегда считается stale.

### B4. Поисковые/НФ-метрики и кросс-регион недоспецифицированы → таргеты непроверяемы
- **Линзы:** performance, missing
- **Где:** `spec/08`, `spec/04`
- **Разрыв:** нет пиковых RPS, бюджета памяти (memtable/Bloom/cache), бюджета
  компакции (write-amplification, макс. число ран, stall), численного RPO/RTO,
  частоты расчёта отсталости. Отдельно: p99 < 20 мс на чтение несовместим с
  кросс-регион клиентом (RTT > 20 мс), без geo-affinity таргет недостижим для
  части пользователей.
- **Рекомендация:** добавить недостающие НФ-метрики; ограничить p99 областью
  «клиент рядом с ДЦ»; добавить строки write/read-RPS и компакции.

## 🟡 Важные

### M1. Кто и как правит корпоративный каталог — не определено (роли/UI)
- **Линзы:** missing
- **Где:** `spec/01` (ПУ-8), `spec/05` (Create/Update/DeleteEmployee), `spec/07` («ролевую модель не вводим»)
- **Рекомендация:** ввести минимальную роль «администратор каталога» и экран правки
  каталога, либо честно вынести изменение каталога за рамки релиза.

### M2. Числовой поиск и канонизация номера несовместимы
- **Линзы:** disputable, missing
- **Где:** `spec/02` (нормализация), `spec/05` (`SearchEmployeeByPhoneExact`),
  `spec/06` (префикс)
- **Рекомендация:** задать семантику (точное по каноническому виду + опциональный
  префикс), индексировать полную и local-формы; переименовать контракт.

### M3. Механизм локальной/глобальной уникальности телефона оставлен «на усмотрение реализации»
- **Линзы:** disputable, missing, performance
- **Где:** `spec/03` (транзакции), `spec/08`
- **Рекомендация:** зафиксировать обязательный механизм (детерминированный
  сериализованный порядок/single-primary + compare-and-set по ключу телефона,
  не MVCC-read-тhen-write); учесть стоимость проверки в бюджете задержки записи.

### M4. Освобождение удалённого номера и tombstones не определено
- **Линзы:** disputable
- **Где:** `spec/02` (I6), `spec/04` (tombstones)
- **Рекомендация:** задать политику переиспользования номера после удаления и роль
  tombstone в уникальность-индексе.

### M5. Семантика version и конкурентных обновлений не ясна
- **Линзы:** missing
- **Где:** `spec/02`, `spec/04`, `spec/05`
- **Рекомендация:** определить version = счётчик записи, модель конфликтов
  (optimistic lock / LWW), что происходит при конкурентном Update.

### M6. Курсор пагинации, колляция, нормализация телефона как формат — недоспецифицированы
- **Линзы:** missing
- **Где:** `spec/06`, `spec/02`
- **Рекомендация:** задать непрозрачный курсор с жизнью/лимитом (default 50),
  byte-порядок на нормализованном UTF-8 (NFC, lower), канон номера (цифры +
  опц. `+`/code), поведение неполного ввода.

### M7. Групповой commit vs per-commit fsync: конфликт для каталога
- **Линзы:** disputable, performance
- **Где:** `spec/03`, `spec/08`, ADR-6
- **Рекомендация:** численно задать окно батчинга; для каталога (ценные записи)
  не применять group commit; проверить p99 < 20 мс при этом.

### M8. Проч. умеренно важное
- Разделение «0 потерь» (локально) vs RPO (регионально) — уточнить формулировки
  durability (disputable G).
- Аутентификация и «текущий пользователь» (token → owner_id) — доопределить (missing Д-3).
- Атомарное применение WAL на репликах/догон после обрыва — контракт (missing Д-6/Д-8).
- Идемпотентность Create при ретраях (missing Д-13); составное чтение каталог+книга
  в ПУ-2 — единый срез (missing Д-14).
- «Низкая задержка» в ADR-6 формулируется избыточно широко (disputable H).
