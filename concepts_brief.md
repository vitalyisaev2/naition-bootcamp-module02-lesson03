# База данных контактов — концепция (итог мозгового штурма)

- **Автор:** студент курса (задание модуля 2, урок 3)
- **Дата:** 2026-10-31
- **Статус:** черновик концепции, вход в формальный проект спецификации

## Overview (кратко, простым языком)

Клиент-серверная система «адресная книга организации» на Go, в которой движок
хранения данных написан с нуля (без готовой СУБД и без embedded-движков).
Система хранит два вида сущностей: **корпоративный каталог сотрудников** (общая
книга, телефон уникален и принадлежит одному сотруднику) и **приватные внешние
книги** (личный круг общения; один номер может лежать у разных сотрудников под
разными именами). Доступ — через веб-интерфейс (TypeScript) и программный API
(gRPC + OpenAPI/grpc-gateway). Ищет имена по телефону и телефоны по имени
(регистронезависимый префиксный поиск). Хранит ~100 тыс. сотрудников × ~200
внешних контактов (~20 млн записей). Отказоустойчивость — три геораспределённых
дата-центра; чтение с отставшей реплики допустимо, но обязательно помечается
пользователю. Атомарность и транзакции при множественных читателях/писателях.

## Analysis

Главные смысловые развязки, к которым пришли в ходе уточнения:

1. **«С нуля» читается буквально.** Запрещены и standalone-СУБД (PostgreSQL,
   Oracle, MySQL, TiDB, CockroachDB…), и embedded-движки (RocksDB, Pebble,
   bbolt, LMDB, SQLite, Badger, LevelDB…). Движок (страницы/файловый формат,
   индексы, WAL, транзакции, репликация) пишем сами. Разрешена стандартная
   библиотека Go и чистые алгоритмические библиотеки (без ответственности за
   персистентность/запросы). → ADR-1.
2. **Модель данных двухуровневая.** Корпоративный каталог (глобальный, общий) +
   приватные внешние книги (личные). → раздел spec/02, ADR-3.
3. **Уникальность телефона (D) — по области действия.** Глобально — только в
   корпоративном каталоге (у сотрудника один рабочий телефон). Для внешних
   книг — локальная уникальность внутри каждой книги; один номер у разных
   сотрудников может зваться по-разному. → ADR-4.
4. **Пересечение 25% внешних контактов не даёт дедупликации.** Записи нельзя
   объединять (у каждого своё имя), поэтому верхняя оценка — честные ~20 млн
   записей. → spec/08 (масштаб).
5. **Поиск.** Регистронезависимый, только префиксный (совпадение с начала
   строки), без транслита. Область: своя приватная книга + корпоративный
   каталог. По чужим внешним книгам поиск не нужен. → spec/06, ADR-5.
6. **Консистентность.** Чтение с отставшей реплики допустимо, но пользователю
   обязательно сообщают, что читают устаревшие данные и что ожидается
   синхронизация. → spec/04, ADR-6.
7. **Средний бизнес.** До 100 тыс. сотрудников, до 200 внешних контактов на
   каждого. Полномасштабный дизайн (не «игрушечный MVP»). → spec/08.

## Goals vs Non-Goals

**В скоупе:**
- Полностью самописный движок хранения на Go: файловый формат, индексы, WAL,
  транзакции, атомарность.
- Двухуровневая модель: корпоративный каталог + приватные внешние книги.
- Веб-UI (TypeScript) и API (gRPC, OpenAPI/grpc-gateway).
- Префиксный регистронезависимый поиск: имя→номера и номер→имена, в рамках
  «своя книга + корпоративный каталог».
- Репликация в 3 геораспределённых ДЦ, отказоустойчивость.
- Удаление контактов (tombstones), глобальная и локальная уникальность телефонов.
- Полномасштабный дизайн.

**Вне скоупа (намеренно):**
- Поиск по чужим внешним книгам (приватность).
- Транслитерация кириллица↔латиница.
- CardDAV — отложен (см. ADR-7).
- Поддержка «придуманных» языковых/нечётких совпадений (fuzzy, опечатки).
- Миграция с существующих систем и обратная совместимость данных (система новая).

## Alternatives Weighed (кратко; полные — в ADR)

- **«С нуля» против использования готовой СУБД.** Выбрали «с нуля» по трактовке
  задания (условие «готовую СУБД использовать не предполагается»). → ADR-1.
- **Модель данных: единый каталог людей против «каталог + приватные книги».**
  Отказались от «единого каталога с глобально уникальным телефоном» — он не
  уживается с фактом «один номер у разных сотрудников под разными именами».
  → ADR-3.
- **Формат репликации: глобальный синхронный кворум против локальный
  primary + асинхронные удалённые реплики.** Выбрали локальный primary с
  асинхронными репликами, компенсируя отставание жёстким требованием помечать
  stale-чтение. → ADR-6.
- **Основной API: только собственный (gRPC/OpenAPI) против открытого CardDAV.**
  CardDAV отложен как вторичный адаптер. → ADR-7.
