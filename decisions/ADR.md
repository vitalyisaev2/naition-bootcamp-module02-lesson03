# ADR — Журнал принятых решений

> Правила ведения: каждое решение нумеруется (ADR-N), фиксируется его мотивация и
> источник (заземление). Агенты и люди ссылаются на номер ADR вместо того, чтобы
> заново «изобретать» решение. Записи дополняются, но не переписываются задним
> числом без нового ADR.
>
> **Источники (заземление):**
> - **З1** — исходная постановка задания курса (модуль 2, урок 3), передана в чате.
> - **З2** — уточнения заказчика/студента в ходе интервью (этот документ, диалог 2026-10-31).
> - **З3** — внешние стандарты (RFC, спецификации).

## ADR-1 — «С нуля»: граница самописного кода
- **Статус:** принято.
- **Решение:** движок хранения (файловый формат страниц, индексы, WAL, транзакции,
  репликация) пишем сами. **Запрещены** standalone-СУБД (PostgreSQL, Oracle, MySQL,
  TiDB, CockroachDB, Redis…) и embedded-движки (RocksDB, Pebble, bbolt, LMDB,
  SQLite, Badger, LevelDB…), т.к. их ответственность — хранение/индексация/запросы.
  **Разрешены** стандартная библиотека Go и чистые алгоритмические библиотеки
  (хеши, сортировки, структуры в памяти, **консенсус** — как «голый алгоритм»),
  не берущие на себя персистентность/запросы. Персистентность лога/снапшотов — всегда
  своя. Подробнее про консенсус — см. ADR-14.
- **Мотивация:** в постановке «с нуля» и «готовую СУБД использовать не
  предполагается»; заказчик подтвердил буквальное прочтение и исключил в т.ч.
  embedded-библиотеки.
- **Альтернативы:** (а) использовать готовую СУБД — отклонено, противоречит
  условию; (б) запретить и stdlib/алгоритмические библиотеки — отклонено, усложняет
  тривиальные вещи без пользы.

## ADR-2 — Масштаб: средний бизнес
- **Статус:** принято.
- **Решение:** целевая нагрузка — до **100 тыс. сотрудников**, до **200 внешних
  контактов** на сотрудника → верхняя оценка ~**20 млн записей** внешних книг +
  ~100 тыс. записей корпоративного каталога.
- **Мотивация:** заказчик снизил планку с «крупной» компании (1 млн) до среднего
  бизнеса; цифры дают значение для НФ-требования и проверяемую оценку.
- **Заземление:** З2.

## ADR-3 — Двухуровневая модель данных
- **Статус:** принято.
- **Решение:** два пространства записей: **корпоративный каталог** (общая книга
  организации, видна всем в поиске) и **приватные внешние книги** (личные, не
  общие; один и тот же номер может встречаться у разных сотрудников под разными
  именами).
- **Мотивация:** заказчик: «внешние контакты общими делать неправильно — у каждого
  свой круг внешнего общения».
- **Альтернативы:** единый глобальный каталог людей — отклонено, не уживается с
  «один номер под разными именами».
- **Заземление:** З2, З1 (требования «искать имена/телефоны»).

## ADR-4 — Уникальность телефона по области действия
- **Статус:** принято (вариант D-1).
- **Решение:** глобальная уникальность («у одного телефона один хозяин») действует
  в **корпоративном каталоге**. Во **внешних книгах** — локальная уникальность
  внутри каждой книги (нельзя хранить один номер дважды в одной книге); глобально
  один номер у разных сотрудников может зваться по-разному.
- **Мотивация:** исходное требование «один телефон — один хозяин» прямо
  конфликтовало с фактом «один номер под разными именами у разных сотрудников»;
  по согласованию уникальность действует там, где осмысленна (каталог), и не воюет
  с пересечением внешних книг.
- **Заземление:** З1 (требование уникальности), З2 (выбор D-1).

## ADR-5 — Семантика поиска
- **Статус:** принято.
- **Решение:** поиск **регистронезависимый**, **префиксный** (совпадение с начала
  строки по имени и по номеру), **без транслита** кириллица↔латиница. Область
  поиска — **своя приватная книга + корпоративный каталог**; по чужим внешним
  книгам поиск не выполняется (приватность).
- **Мотивация:** заказчик: «транслит не нужен, обойдёмся префиксным поиском»;
  «поиск по чужим внешним книгам не нужен».
- **Заземление:** З2.

## ADR-6 — Консистентность и формат репликации
- **Статус:** принято (предложение автора, требует финального подтверждения).
- **Решение:** запись идёт в **логический primary (лидер)**, достижимый с низкой
  задержкой; на два удалённых ДЦ изменения реплицируются **асинхронно** (только
  закоммиченный лог). Чтение с реплики, которая отстаёт, допустимо, **но
  пользователю обязательно сообщают**, что данные могут быть устаревшими и ожидается
  синхронизация. RPO ненулевой.
- **Мотивация:** заказчик разрешил stale-чтение при обязательной пометке; это даёт
  низкую задержку записи против стоимости синхронного глобального кворума.
- **Альтернативы:** глобальный синхронный кворум (Raft через 3 ДЦ) — отклонён из-за
  задержки синхронных круготёков на каждую запись; потребует отдельного подтверждения,
  если требования к RPO ужесточатся.
- **Заземление:** З2.

## ADR-7 — CardDAV отложен
- **Статус:** принято.
- **Решение:** CardDAV (RFC 6352) в основной контракт **не входит**, отложен как
  опциональный вторичный адаптер поверх движка. Основной API — собственный
  (gRPC + OpenAPI/grpc-gateway).
- **Мотивация:** CardDAV — точный по смыслу стандарт адресной книги, но полная
  реализация RFC 6352 (WebDAV/XML/vCard, PROPFIND/REPORT/MKCOL, sync-token) — крупный
  отдельный протокольный слой; как вторичный адаптер даёт совместимость с реальными
  клиентами (iOS/macOS/Thunderbird).
- **Заземление:** З2 (отложен), З3 (RFC 6352, RFC 6350). Подробнее — spec/00, spec/05.

## ADR-8 — Язык веб-интерфейса: TypeScript
- **Статус:** принято.
- **Решение:** веб-интерфейс пишем на **TypeScript**.
- **Мотивация:** для приложения с собственным API (контракты gRPC/OpenAPI), командой и
  длительной поддержкой TS даёт типы на стыке с контрактами (можно генерировать из
  proto), безопасный рефакторинг. Чистый JS оправдан лишь для крошечных утилит.
- **Заземление:** З2 (вопрос «JS или TS в 2026», рекомендация автора).

## ADR-9 — Удаление и атомарность
- **Статус:** принято.
- **Решение:** поддерживается удаление контактов; при репликации удаление ведётся
  через **tombstones** (чтобы часовые метки/конфликты не «воскресили» удалённое).
  Операции создания/обновления/удаления — атомарные и транзакционные (WAL + индексы
  обновляются согласованно).
- **Мотивация:** заказчик подтвердил необходимость удаления; модальность записи
  (несколько индексов) требует атомарности.
- **Заземление:** З2 (удаление нужно), З1 (атомарность/транзакционность).

## ADR-10 — Полномасштабный дизайн (не MVP)
- **Статус:** принято.
- **Решение:** спецификация описывает реалистичный полномасштабный дизайн (движок +
  3 ДЦ + репликация + API + UI), а не ограниченный MVP.
- **Мотивация:** заказчик выбрал «полномасштабный дизайн»; целевая планка —
  честная реалистичная система, код по которой будет сравнивать ведущий курса.
- **Заземление:** З2.

## ADR-11 — Failover и fencing при потере primary (по итогам ревью, rev v0.2)
- **Статус:** принято.
- **Решение:** при потере первичного региона один из удалённых read-ДЦ промоутится в
  новый primary по явной процедуре (auto/под управлением оператора — настраивается),
  теряя только «хвост» unreplицированного WAL ≤ RPO. Промоушен **обязан**
  сопровождаться **epoch/lease (fencing)**: пишет только узел со старшей эпохой,
  записи со старой эпохой отклоняются (защита глобальной уникальности I2 от
  split-brain). Синхронный Raft-перевыбор — только в границах действующего кворума.
- **Мотивация:** ревью (блокеры B1, B2) показало, что «Raft-перевыбор на
  оставшихся узлах» невыполним, т.к. удалённые ДЦ не члены первичной Raft-группы, а
  без fencing возможен «split-brain» с нарушением уникальности телефона.
- **Альтернативы:** (а) включить удалённые ДЦ в единый глобальный Raft-кворум —
  RPO=0, но высокая задержка записи, конфликт с p99, противоречит ADR-6;
  (б) «ручной промоушен» без fencing — небезопасно по I2.
- **Заземление:** `reviews/goldfish_review_report.md` (B1, B2), spec/04.

## ADR-12 — Stale-пометка: «current» = отставание ниже порога
- **Статус:** принято.
- **Решение:** асинхронная реплика не запрашивает primary синхронно на каждый read.
  Категория результата чтения определяется по **last-known позиции primary**
  (heartbeat) против применённого LSN: `current` = отставание < порога `T_stale`
  (по умолчанию ≤ 5 с), иначе `stale`. При недостоверной позиции — всегда `stale`.
  «Никогда не сообщать свежее, когда данные могут быть устаревшими».
- **Мотивация:** ревью (блокер B3): «current» невычислим в чистом async без
  синхронного запроса; правило сдвигает погрешность в сторону stale.
- **Альтернативы:** (а) синхронная сверка LSN на каждый read — теряет асинхронность;
  (б) помечать всё — неинформативно.
- **Заземление:** `reviews/goldfish_review_report.md` (B3), spec/04.

## ADR-13 — Ролевая модель: каталог ведёт администратор (M1 resolved)
- **Статус:** принято.
- **Решение:** корпоративный каталог обслуживает **администратор каталога**
  (create/update/delete записей сотрудников); персональную книгу внешних контактов
  ведёт **сам сотрудник** (свои записи). Обычный сотрудник каталог только читает;
  чужие приватные книги не видны никому, включая админа (принцип владельца I5).
- **Мотивация:** ревью (M1) выявило противоречие «каталог нужно вести, но ролевую
  модель не ввели»; заказчик постановил явно разделить права.
- **Альтернативы:** (а) любой сотрудник правит каталог — слабо по целостности общих
  данных; (б) вынести правку каталога из релиза — оставило бы каталог необслуживаемым.
- **Заземление:** `reviews/goldfish_review_report.md` (M1), решение заказчика 2026-10-31.

## ADR-14 — Консенсус: алгоритмическая библиотека + своё хранилище/обвязка
- **Статус:** принято.
- **Решение:** для консенсуса используем зрелую Go-библиотеку — **`go.etcd.io/raft`
  или `hashicorp/raft`** — как «чистый алгоритм» (лидер-выбор, репликация лога,
  leaderless-learners, снапшоты). **Персистентность лога и снапшотов — своя**:
  подключаем собственные `LogStore`/`SnapshotStore` поверх нашего движка (не bbolt/MDB).
  Свои и пишем: fencing/epoch, перенос primary (промоушен learner), stale-индикацию,
  discovery, кворум по регионам. Механизм уникальности телефона (CAS, spec/03) —
  поверх порядка лога.
- **Мотивация:** анализ объёмов показал, что консенсус **не является узким
  местом**: 20 млн записей живут в нашем LSM-движке; через Raft идут только команды
  записи (write-RPS ~сотни–тысячи), а объёмные переносы решаются **снапшотами**
  (подтверждено README `hashicorp/raft`: snapshot+log compaction). Обе библиотеки
  держат `10⁴–10⁵` мелких writes/с — с запасом. Переписывать консенсус вручную —
  ошибкоопасно (это подчёркивало ревью, блокер B1/B2); «с нуля» сохраняется для всего
  персистентного и интеграционного слоя.
- **Альтернативы:** (а) писать консенсус самим — больше работы и риск, не даёт
  выгоды по данным; (б) использовать готовую квотовую СУБД (CockroachDB и т.п.) —
  запрещено ADR-1.
- **Заземление:** анализ объёмов (этот диалог), документ `hashicorp/raft` (README:
  snapshotting, non-voting servers, fault tolerance 3/5, «performance bound by disk
  I/O and network latency»), ADR-1 (чистые алгоритмические библиотеки разрешены).
